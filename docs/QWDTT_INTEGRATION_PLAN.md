# qWDTT в WhiteZia: оценка интеграции

План обновлён 3 ноября 2026 года (Asia/Yekaterinburg). Исходники qWDTT исследованы
2 ноября. Статус: **запланировано, не реализовано и не развёрнуто**. qWDTT не
собирался/не запускался для приёмки, работа через SIM не подтверждена.

Целевое поведение, согласованное в обсуждении: автоматическое подключение без
ручного выбора сервера, ввода хешей и реквизитов. Core выдаёт параметры устройства.
При требовании капчи пользователь проходит её в окне внутри WhiteZia;
после успеха подключение продолжается автоматически. Системное VPN-разрешение
при первом запуске остаётся действием пользователя.

## Какие проекты найдены

- [SpaceNeuroX/proxy-turn-vk-android](https://github.com/SpaceNeuroX/proxy-turn-vk-android)
  — qWDTT, проверенный master и релиз v1.4.4:
  `a296c57eaba69bb9479a24f9157856490890e47d`.
- [makriq-org/qwdtt](https://github.com/makriq-org/qwdtt) — связанный форк;
  проверенный master `684769a74531a8e0454eb347b041bc7c29d897a3`.
  Включает слияние указанного upstream и дополнительные тесты.
- [ildarmaga/wdtt](https://github.com/ildarmaga/wdtt) — совместимый серверный
  вариант с панелью, API и маршрутизацией через Xray. Для первого стенда
  предпочтительнее согласованная пара клиента и сервера из одного коммита
  SpaceNeuroX; совместимость другого сервера требует отдельной проверки.

qWDTT передаёт трафик через TURN-инфраструктуру звонков VK к собственному VPS.
Есть WireGuard, локальный SOCKS5 поверх userspace WireGuard и raw-IP режим.
Это отдельный транспорт; поддержки qwdtt:// в Xray 26.10.31 от этого не появляется.
Работа при ограничениях конкретного мобильного оператора пока не подтверждена.

## Этапы включения и автоматический режим

Технический прототип «VK TURN (экспериментальный)» может использовать ручной
импорт wdtt:// / qwdtt:// для стенда. Это не требование к конечному пользователю:
целевой режим получает конфигурацию из подписки и подключается автоматически.
До приёмки нового транспорта оставить действующий автоматический порядок
direct Xray → CDN Xray → CottenDNS. После успешных полевых проверок можно отдельно
включить новую цепочку: direct Xray → CDN Xray → qWDTT → CottenDNS.

Для первого прототипа использовать уже имеющийся в Go-клиенте `-mode socks`:

Приложения → существующий Android TUN / tun2proxy → локальный SOCKS5 qWDTT →
userspace WireGuard → транспорт TURN/DTLS/WRAP → собственный wdtt-server → интернет.

Реализовать QwdttProcessManager на основе ExternalProcessRunner; единственным
владельцем Android VPN оставить WhiteZiaVpnService. Не переносить вторые VPN-сервисы,
интерфейс, установщик серверов, собственные аккаунты и Telegram-бот upstream.
SOCKS слушает только loopback с одноразовыми реквизитами аутентификации.
Сокеты транспорта должны идти через физическую сеть; проверить действующее
исключение UID приложения из VPN и восстановление после смены сети.

Точки расширения WhiteZia:

- vpn/WhiteZiaVpnService.kt: запуск/остановка, готовность, health и восстановление.
- vpn/VpnConnectionOrchestrator.kt: новый тип кандидата; общий mutex и границы
  остановки остаются обязательными.
- runtime/ExternalProcessRunner.kt: отдельный процесс, завершение, очистка файлов,
  контролируемый канал команд/событий.
- model/WhiteZiaProfileLinks.kt, SubscriptionProfileManager.kt,
  SubscriptionConnectionPreparer.kt: конфигурация, импорт и полная замена снимка.
  Отсутствующий qWDTT в новой подписке не должен наследовать чужие старые ключи.
- Снимки запуска и восстановления VPN, выбор режима, состояние и диагностика.

## Сравнение вариантов

| Вариант | Преимущество | Ограничение / объём изменений |
| --- | --- | --- |
| Go SOCKS5 + наш tun2proxy | Использует существующий TUN, FakeDNS и управление процессами; удобен для первого стенда | В проверенном socks5.go реализован TCP CONNECT и IPv4; нет готового пути application UDP |
| Дополнить SOCKS5 поддержкой UDP | Можно сохранить текущую архитектуру TUN/tun2proxy и добавить UDP-приложения | Нужны UDP ASSOCIATE, согласование с tun2proxy, DNS, MTU, очистка ассоциаций и отдельные тесты |
| Raw-IP с передачей TUN fd | Upstream уже имеет такой режим; переносит IP-пакеты без SOCKS/WireGuard-слоя | Более глубокое вмешательство в владение TUN, DNS/FakeDNS и переключение маршрутов; требуется отдельный разбор безопасности протокола |

В первом варианте нельзя обещать работу звонков, игр и QUIC. Существующий
UDP-трафик нельзя выпускать напрямую при отказе прокси. DNS/FakeDNS нужно
проверить через TCP-путь; IPv6 либо туннелировать после доработки, либо блокировать
внутри VPN. В raw-режиме старый FakeDNS reader не переносится автоматически:
нужен согласованный переход с корректным завершением старой VPN/DNS-сессии.

## Капча и жизненный цикл подключения

- Без запроса капчи соединение устанавливается автоматически. Не обещать, что
  проверка VK больше никогда не появится: её частота определяется внешним сервисом.
- В открытом приложении показывать встроенную страницу проверки VK в WebView,
  поддерживающую ползунок/картинки. После успешного ответа продолжать ту же попытку.
- В фоне или при заблокированном экране показывать уведомление с переходом в
  приложение. Не использовать overlay или самопроизвольный полноэкранный запуск.
  Если уведомления запрещены, сохранять состояние до открытия приложения только
  в пределах действующей сессии/срока; затем корректно завершать ожидание.
- Состояние WaitingForCaptcha не является Connected. Для него нужен отдельный
  ограниченный срок ожидания, не обычный короткий таймаут запуска SOCKS/Xray.
- Один активный запрос на попытку: request_id + VPN session_id + срок действия.
  Параллельные воркеры не должны открывать несколько окон.
- Stop, выход из аккаунта, смена профиля/маршрута и новый запуск отменяют старый
  запрос, закрывают WebView и уничтожают токен. Поздний ответ не запускает VPN.
- При отмене или таймауте автоматический режим продолжает следующий разрешённый
  канал, включая CottenDNS с его существующей сетевой политикой. Остановка
  пользователем всего VPN не запускает fallback. Не допускать бесконечных циклов
  проверки и незаметного переключения с уже успешно подключённого канала.
- HTTPS URL, перенаправления и JS bridge ограничить проверенными доменами капчи;
  не игнорировать ошибки TLS. Команды/ответы передавать по закрытому каналу,
  исключить URL с токенами, cookies и ответы капчи из пользовательских логов.
- Предусмотреть истёкшую капчу, процесс death/пересоздание Activity и смену сети:
  старый запрос не восстанавливать как действующий без проверки идентичности.

Upstream содержит CAPTCHA_SOLVE / CAPTCHA_RESULT и отдельную Activity для ручной
проверки, но их требуется адаптировать к границам сессий WhiteZia.
[Исходник](https://github.com/SpaceNeuroX/proxy-turn-vk-android/blob/a296c57eaba69bb9479a24f9157856490890e47d/app/src/main/java/com/wdtt/client/vk/ManlCaptchaWebViewManager.kt),
[ограничения запуска окон в фоне Android](https://developer.android.com/guide/components/activities/secure-bal).

## Сервер и существующие подписки

Нужен собственный qWDTT-шлюз. Начать с изолированного стенда, отдельных портов,
своих тестовых реквизитов и ограничений ресурсов. Сервисы Xray/CottenDNS не заменять.
Интеграция Xray на сервере — возможный способ дальнейшего egress, а не обязательный
дополнительный Xray на телефоне.

Core остаётся источником истины для подписок и купленных 3–6 мест. Для каждого
существующего Core device_id выдавать отдельный qWDTT-пароль, ограниченный одним
устройством на шлюзе. Один телефон с несколькими транспортами занимает одно место.
Нужны идемпотентные выдача, продление и отзыв реквизитов: удаление устройства,
истечение подписки и блокировка должны отключать qWDTT так же, как другие каналы.
Проверенный сервер имеет admin API создания/обновления/деактивации реквизитов,
но адаптер ещё не написан. API шлюза не выдаётся клиентскому приложению.
В проверенном API обновление `days` пересчитывает срок от текущего момента:
для точного срока Core потребуется доработка или иной проверенный метод
синхронизации, без повторного продления при retry. Создание случайных паролей
также нужно сделать идемпотентным относительно операции Core.

В managed bundle можно добавить опциональный блок qwdtt со списком узлов,
параметрами транспорта, хешами звонков и реквизитами конкретного устройства.
Схему и обработку старым APK проверить контрактными тестами; совместимость
существующего stormbundle:// сохраняется. Включение для клиентов контролировать
возможностями/версией APK и серверным флагом.

## Что нужно проверить до включения пользователям

1. **VK-зависимость.** Получение временных TURN-реквизитов, закрытые/истёкшие
   хеши звонков, ограничения API и капча. При необходимости интерактивного действия
   показывать явное состояние и не блокировать автоматическое переключение.
   Успех одного звонка или Wi-Fi не доказывает работу через SIM.
2. **Реквизиты и аутентификация сервера.** main.go печатает полученный WG-конфиг
   и сохраняет wg-turn.conf; такую выдачу секретов в обычные логи убрать.
   session.go использует InsecureSkipVerify в DTLS; в контексте WRAP и выдачи
   WG-ключей нужна отдельная проверка привязки к нашему серверу. Это наблюдения
   по коду, не подтверждение эксплуатации или полноценный аудит.
3. **Native-сборка.** Собрать ARM64/ARMv7 из закреплённого исходника на нашем Go,
   проверить зависимости отдельно от Xray, ELF/ZIP 16 КиБ, лицензии и хеши.
   У upstream есть x/net v0.57.0 и compress v1.18.2: обновлённые зависимости
   встроенного Xray не обновляют отдельный qWDTT-бинарник.
4. **Лицензия.** qWDTT использует GPL-3.0. Перед распространением встроенной
   версии определить лицензионную совместимость и комплект соответствующих
   исходников/уведомлений. CONTRIBUTING.md и CLA.md WhiteZia сейчас описывают
   source-available/proprietary условия: это явная нерешённая граница перед
   включением GPL-компонента. Этот план не меняет лицензию проекта и не разрешает
   несовместимое распространение. Отдельный процесс сам по себе вопрос не решает.
5. **Приёмка.** Реальный HTTPS/Telegram-трафик, TCP DNS, отсутствие DNS/IPv6/UDP
   утечек, смена Wi-Fi/мобильной сети, сон/перезапуск процесса и Stop.
   Проверить расход батареи/RAM и нагрузку шлюза. Для расширенного варианта —
   UDP DNS, звонки/QUIC и длительные сессии. Отдельно: исчерпание 3–6 мест,
   отзыв устройства, истечение и продление подписки, отключение узла.

## Последовательность работ

1. Закреплённая сборка Go-клиента, очистка секретных логов, проверка зависимостей
   и аутентификации сервера; изолированный стенд со своим тестовым доступом.
2. Debug WhiteZia с ручным режимом SOCKS/TCP и импортом профиля. Проверка на
   настоящих SIM в нужных сетях. Решение, полезен ли транспорт на практике.
3. При положительном результате — Core provisioning и отзыв, выдача профиля
   существующему устройству, автоматическое подключение с описанным окном капчи
   для ограниченной группы пользователей.
4. Отдельно выбрать путь UDP и только после приёмки обсуждать автоматический
   fallback перед CottenDNS и массовое включение.
